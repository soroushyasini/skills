# راهنمای تصمیم و ممیزی نسخه ۲

این مرجع برای مرزهای حساس دسته‌ها و اعتبار شواهد است. عنوان شغلی اصلی کاربر توسعه‌دهنده سامانه‌های سازمانی است؛ نقش همکار قبلی یا درخواست‌کننده، جای تحلیل خروجی را نمی‌گیرد.

## سه تصمیم مستقل

- دسته: چه خروجی سازمانی تولید می‌شود؟ برای هدف صریحاً شخصی، دسته Personal یک استثنای هدف‌محور است تا مصرف وقت خارج از فعالیت شرکت آشکار بماند.
- ارتباط با نقش: نقش اصلی است یا پوشش مسئولیت‌های فرایند/QA، IT یا دفتر؟ منشأ واقعی تخصیص را از کاربر بگیر؛ از رنگ نتیجه نگیر.
- وضعیت قرارداد: چه شاهدی درباره شرح وظایف اولیه یا قرارداد وجود دارد؟ پوشش نقش و رسمی‌شدن آن را یکی فرض نکن.

تگ‌های قدیمی تأییدشده کاربر حفظ می‌شوند. درخواست شخصی تازه، منفعت سازمانی یا MANAGEMENT VALUE خودکار ندارد؛ حفظ یک تگ قدیمی تأییدشده با افزودن تازه آن تفاوت دارد.

## Process، Quality و Analysis

| خروجی غالب | دسته |
|---|---|
| مدل وضع موجود، مسئله و گلوگاه، نقش و کنترل روش کار | Process |
| وضع مطلوب، مقایسه گزینه‌ها و نقشه‌راه بهبود | Process |
| رفتار سامانه، مدل داده و مشخصات قابل ساخت | Analysis |
| ارزیابی عملکرد یا انطباق نسبت به معیار مشخص و یافته قابل ردیابی | Quality |
| علت‌یابی و بررسی اثربخشی رفع عدم انطباق | Quality |
| طراحی راهکار اصلاح فرایند پس از یافته | Process |
| اجرای روش جدید و مدیریت پذیرش اصلاح | Process؛ مرحله اجرا و پذیرش |
| ثبت موعد و دریافت مدرک بدون ارزیابی | Coordination |

تحلیل شکاف، روش مشترک است. اگر هدف تشخیص مسئله برای طراحی بهبود است Process؛ اگر سنجش نسبت به معیار و تولید نتیجه ارزیابی است Quality. ممیزی داخلی و آمادگی ممیزی با معیار و شواهد، Quality است. صرف ذکر ISO، کلمه «کنترل» یا عنوان کارشناس تضمین کیفیت کافی نیست.

مرز طراحی تا اجرا را در کارت مرکب از خروجی نهایی آن تعیین کن؛ اگر یافته، طراحی اصلاح و اجرای تغییر هر کدام تحویل مستقل دارند، تفکیک پیشنهاد شود. برای کاربر مسئولیت یا صلاحیت ممیز، مالک QMS، مدیر تحول یا عنوان حرفه‌ای تازه نساز.

## Development، Deployment و Support

- نقص کد، ساخت قابلیت و آزمون صحت رفتار نرم‌افزار: Development.
- انتشار و محیط عملیاتی، زیرساخت و سرویس مشترک، مهاجرت کنترل‌شده، بک‌آپ سامانه و بازیابی: Deployment.
- دستگاه، نرم‌افزار نصب‌شده و تنظیمات یا دسترسی محلی کاربر: Support.
- ساخت اسکریپت مستقل برای دریافت داده یا قابلیت سازمانی: Development.
- اسکریپت جزئی از مدیریت زیرساخت یا اجرای برنامه عملیاتی بک‌آپ: Deployment.

ملاک صرف تعداد افراد متأثر نیست؛ منشأ و هدف اقدام را بررسی کن. مشکل یک نفر می‌تواند از سرویس مشترک باشد. ساخت API سبز، انتشار API آماده بنفش و راهنمای مستقل انتشار زرد است.

آماده‌سازی لپ‌تاپ سازمانی Support است. فعال‌سازی حساب صریحاً شخصی مدیر Personal است و ماهیت اقدام فنی در توضیح حفظ می‌شود. گوشی مدیر با هدف نامعلوم را خودکار Personal نکن. اتصال DGPS به رایانه می‌تواند Support باشد؛ حمل باتری مگنومتر یا آزمون تخصصی آن را صرف تجهیز بودن IT فرض نکن.

## BI، آزمون نرم‌افزار و امور اداری

| اقدام | دسته و شرط |
|---|---|
| رفع تکرار و یکسان‌سازی دیتاست مدعوین | BI؛ خروجی مجموعه‌داده مستقل |
| رونویسی چند عدد برای تکمیل پرونده | Coordination |
| استخراج تصاویر به مجموعه‌داده ساختاریافته مستقل | BI؛ صرف جدول بودن کافی نیست |
| ساخت اسکریپت دریافت و تبدیل داده LME | Development |
| مقایسه قیمت نمونه برای آزمودن اسکریپت | Development |
| پذیرش کیفیت دیتاست با کنترل تاریخ، واحد و مرجع | BI |
| اجرای Import و کنترل صحت انتقال به محیط عملیاتی | Deployment |
| محاسبه و تفسیر روند KPI | BI |
| تعیین KPI به‌عنوان کنترل روش مطلوب | Process |
| بررسی انطباق اجرای پایش با معیار نظام کیفیت | Quality |

داده آماده، بینش تحلیلی و قابلیت نرم‌افزاری سه خروجی متفاوت‌اند. با گسترده‌ترشدن نارنجی، نوع خروجی در توضیح ضروری است؛ هر فعالیت مرتبط با اطلاعات، تحلیل داده نیست.

## Documentation و Coordination

- طراحی سند، محتوای قالب، لیبل یا راهنما: Documentation.
- درج اطلاعات در قالب تعیین‌شده برای یک نامه یا پرونده: Coordination.
- کنترل نسخه، نمایه و نگهداری دارایی اطلاعاتی: Documentation.
- تعیین قواعد تصویب، مسئولیت‌ها و کنترل فرایند: Process.
- ساخت تولیدکننده خودکار نامه: Development.
- آموزش امکانات یا روش مصوب: Documentation؛ رفع موردی مشکل کاربر Support.
- برنامه آمادگی و پذیرش شامل تغییر روش، بازخورد و رفع موانع: Process؛ مرحله برنامه‌ریزی یا اجرا و پذیرش.

یک‌بارمصرف بودن سند، طراحی محتوا را حذف نمی‌کند. واژه «اصلاح قالب» می‌تواند طراحی واقعی یا اصلاح اطلاعات پرونده باشد؛ سهم اقدام را بررسی کن.

داخلی یا بیرونی بودن مخاطب در توضیح ثبت می‌شود. تماس با کارگزاری برای مدرک بیمه Coordination است. مذاکره شرایط همکاری نیز در خانواده اداری/هماهنگی ثبت می‌شود، با نتیجه توافق یا مذاکره روشن؛ External کلاس جدا نسخه ۲ نیست.

بسته جلسه و صورت‌جلسه از مطالب موجود Coordination است. تحلیل داده برای مدیر BI، نقشه‌راه برای مدیر Process، طراحی سامانه برای مدیر Analysis. تهیه بسته شواهد بازنگری مدیریت بدون قضاوت تخصصی می‌تواند Coordination باشد؛ ارزیابی نظام کیفیت و تحلیل شواهد آن Quality، با حفظ سهم واقعی فرد.

## Personal و هدف سازمانی

شخصی بودن از هدف صریح تعیین می‌شود، نه مقام درخواست‌کننده یا قضاوت درباره ارزش کار. تکلیف دانشگاهی شخصی مدیر و گیفت‌کارت حساب شخصی او مثال‌های تأییدشده‌اند. پروژه آموزشی یا پژوهشی مرتبط با شرکت را به دلیل نام دانشگاه خودکار Personal نکن.

Personal یک استثنای عمدی در طبقه‌بندی خروجی سازمانی است. ماهیت ثانویه اقدام مثل تنظیم حساب، نگارش یا استخراج داده در شرح حفظ شود. در گزارش مقایسه نقش اصلی با کارهای دیگر، وقت این دسته جدا بماند. از تعبیر «بیخودی»، «خدمتکاری» یا نسبت‌دادن انگیزه به درخواست‌کننده استفاده نکن.

عنوان نمونه: [Personal] فعال‌سازی گیفت‌کارت حساب شخصی اپل.
برای درخواست دانشگاهی، اقدام واقعی مثل کمک، ویرایش یا آماده‌سازی را حفظ کن؛ نوع تکلیف، سهم فرد و نتیجه را نساز. طبقه‌بندی این سابقه مجوز انجام درخواست تازه‌ای نیست.

## وضعیت کار، شواهد و قرارداد

تسک برنامه‌ریزی‌شده برای ساخت، از ابتدا Development است. اگر کار فقط تحقیق امکان‌پذیری یا طراحی راهکار را تعهد می‌کند Analysis است. از ستون برد یا «هنوز نساخته‌ایم» به‌تنهایی دسته نتیجه نگیر. خروجی توافق‌شده، پیشرفت، تحویل و اثر چهار مفهوم جدا هستند.

| ادعا | شاهد مناسب |
|---|---|
| مدل اولیه فرایند | منابع شناخت، دامنه و موارد نامعلوم |
| وضع مطلوب | تغییر طراحی‌شده، مسئولیت و معیار بررسی |
| نیازمندی سامانه | منبع نیاز، رفتار و معیار پذیرش |
| قابلیت ساخته‌شده | نسخه، آزمون یا پذیرش بیان‌شده |
| بازیابی موفق | محیط و نتیجه آزمون بازیابی |
| یافته عدم انطباق | معیار قابل اعمال و شاهد نقض |
| اثربخشی اقدام اصلاحی | بررسی پس از اجرا و معیار نتیجه |
| پذیرش روش جدید | استفاده واقعی، بازخورد یا تغییر رفتار |
| منفعت اندازه‌گیری‌شده | شاخص، خط مبنا و مقایسه قابل دفاع |

سند، نصب، استفاده، پذیرش و منفعت را هم‌معنا ننویس. مدل مصاحبه یک فرد، مدل تأییدشده سازمان نیست. بدون معیار و شاهد، مشاهده نیازمند بررسی یا شکاف احتمالی بنویس. نسخه استاندارد و بند را از زمینه معتبر بگیر؛ منابع آموزشی نسخه ۲۰۱۵، نسخه قابل اعمال امروز را تعیین نمی‌کنند.

کاربر پوشش وظایف همکار قبلی، تیم IT و دفتر را تأیید کرده است. این سابقه، منشأ مسئولیت را روشن می‌کند؛ همه فعالیت‌های هر رنگ را بیرون قرارداد اعلام نکن. تگ‌های BEYOND CONTRACT، HIGH IMPACT و MANAGEMENT VALUE موجود قبلاً تأیید شده‌اند و باید حفظ شوند.

## منابع و حدود کاربرد

منابع منتخب هنگام بازنگری ۵ اکتبر ۲۰۲۶ بررسی شدند. نگاشت ده دسته محلی است؛ منابع، قرارداد، صلاحیت حرفه‌ای یا سمت رسمی کاربر را تعیین نمی‌کنند.

- [SFIA 9: Business process improvement — BPRE](https://sfia-online.org/en/sfia-9/skills/business-process-improvement): طراحی و بهبود روش کار؛ شناخت، طراحی و اجرای بهبود در خانواده Process، با مرحله مشخص، ثبت می‌شوند.
- [SFIA 9: Quality assurance — QUAS](https://sfia-online.org/en/sfia-9/skills/quality-assurance): ارزیابی، ممیزی، یافته و اثربخشی اصلاح؛ پشتوانه تفکیک Quality از طراحی فرایند و آزمون کد.

- [SFIA 9: Application support — ASUP](https://sfia-online.org/en/sfia-9/skills/application-support): پشتیبانی برنامه عملیاتی؛ کلاس Support در این اسکیل همچنین پشتیبانی دستگاه و کاربر را به‌عنوان تفکیک محلی پوشش می‌دهد.
- [SFIA 9: Data engineering — DENG](https://sfia-online.org/en/sfia-9/skills/data-engineering): آماده‌سازی و کیفیت داده در کنار ساخت و عملیات خط لوله؛ نگاشت محلی حسب خروجی بین سبز، بنفش و نارنجی تقسیم می‌شود.
- [SFIA 9: Content design and authoring — INCA](https://sfia-online.org/en/sfia-9/skills/content-design-and-authoring): دارایی محتوایی متنی و تصویری.
